# Specification: User Activity Tracking Service

## Overview

A lightweight Go REST API service backed by PostgreSQL that ingests user activity events, exposes filtered query endpoints, and runs a background aggregation job every 4 hours. Includes a minimal React web client for viewing events.

---

## 1. Data Models & Schemas

### 1.1 Events Table (`events`)

Stores raw activity events ingested via the REST API.

| Field | Type | Description |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | Unique internal identifier (generated by backend/DB). |
| `user_id` | `BIGINT` | Identifier of the user triggering the action. Indexed. |
| `action` | `VARCHAR(64)` | Event name (e.g., `page_view`, `button_click`, `login`). |
| `metadata` | `JSONB` | Flexible key-value payload (e.g., `{"page": "/home", "ip": "..."}`). |
| `created_at` | `TIMESTAMPTZ` | Timestamp when the event occurred/was recorded (defaults to `NOW()`). Indexed. |

### 1.2 Aggregated Stats Table (`user_activity_stats`)

Stores periodic aggregations computed by the background job.

| Field | Type | Description |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | Unique stat record ID. |
| `user_id` | `BIGINT` | User identifier. Indexed. |
| `event_count` | `INTEGER` | Total events recorded for this user within the interval. |
| `period_start` | `TIMESTAMPTZ` | Start timestamp of the 4-hour aggregation window. |
| `period_end` | `TIMESTAMPTZ` | End timestamp of the 4-hour aggregation window. |
| `created_at` | `TIMESTAMPTZ` | Timestamp when this aggregate record was calculated. |

## 2. API Endpoints

### 2.1 Ingest Event

* **Method:** `POST`
* **Path:** `/api/v1/events`
* **Request Body:**

```json
{
  "user_id": 42,
  "action": "page_view",
  "metadata": {
    "page": "/home"
  }
}

```

*(Note: `id` and `created_at` are generated server-side upon insertion).*

* **Response:** `201 Created`

```json
{
  "id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11",
  "user_id": 42,
  "action": "page_view",
  "metadata": {
    "page": "/home"
  },
  "created_at": "2026-08-15T18:00:00Z"
}

```

### 2.2 Retrieve Filtered Events

* **Method:** `GET`
* **Path:** `/api/v1/events`
* **Query Parameters:**
* `user_id` *(optional)*: `int` (filter by specific user)
* `from` *(optional)*: ISO 8601 string / RFC3339 (e.g., `2026-08-01T00:00:00Z`)
* `to` *(optional)*: ISO 8601 string / RFC3339 (e.g., `2026-08-15T23:59:59Z`)


* **Response:** `200 OK`

```json
[
  {
    "id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11",
    "user_id": 42,
    "action": "page_view",
    "metadata": {
      "page": "/home"
    },
    "created_at": "2026-08-15T18:00:00Z"
  }
]

```

---

## 3. Background Aggregation Job

* **Interval:** Every 4 hours (configurable via `CRON_INTERVAL` / `AGGREGATION_INTERVAL` env var for testing, default `4h`).
* **Behavior:**
1. Calculates the time range: `[now - 4h, now]`.
2. Aggregates the number of events per `user_id` recorded in `events` during that window.
3. Inserts calculated records into `user_activity_stats`.


* **Execution Strategy:** In-process worker (via Go standard `time.Ticker` or `robfig/cron/v3`) initialized alongside the HTTP server with graceful shutdown handling.

---

## 4. Frontend Client (React)

A minimal Single Page Application (Vite + React) that allows checking events:

* Input field for `user_id`.
* Date range pickers (`From` and `To`).
* "Fetch Events" button.
* Simple responsive table/list displaying matching events (`id`, `user_id`, `action`, `metadata`, `created_at`).

---

## 5. Technical Stack & Deliverables

* **Backend:** Go (`net/http` or lightweight router like `chi`), PostgreSQL.
* **Frontend:** React (Vite).
* **Containerization:** `docker-compose.yml` orchestrating:
1. `postgres` (database)
2. `backend` (Go API + background job)
3. `frontend` (React app)


* **Configuration:** Root `.env.example` defining database credentials, ports, and aggregation frequency.
* **Documentation:** `README.md` containing local/Docker startup commands, sample curl commands, and architecture overview.
